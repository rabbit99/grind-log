## 目的

天堂看不到單隻怪物的經驗，只能靠經驗條的變化推估；而且等級越高，升一級要的經驗越多，
「看不到終點」很容易讓人放棄。這個功能把「目標」拆成**具體的時段表**：

1. 使用者輸入現在的等級與%、想達到的等級、期限、每週可以練的時段。
2. 系統算出整段期間每個時段「該到哪個位置」，輸出一張表。
3. 時段進行中時，那一列會被標出來；時段結束後，使用者填「完成」或「沒練」。
4. 摘要區顯示完成了多少、有沒有落後、剩下的時段要多快才補得回來。

計畫是**目標與提醒**，不是實際成績：實際獲得多少%，仍然記在「練功記錄」頁。

## 介面

第三個頁籤「練功計畫」`#tabPlan`，面板 `#pagePlan`（整頁切換，跟「每日進度」一樣，不動原本兩頁的版面）：

- 沒有計畫時：簡短說明 `#planEmpty` ＋ 條件表單 `#planForm`。
- 有計畫時：摘要 `#planSummary` → 排程表 `#tblPlan`（分頁 `#planPager`）→ 摺疊的「修改條件」`#planEdit`（內含同一份表單）。
- 訊息區 `#planMsg`（`role="alert"`，紅字，沒有訊息時隱藏）。
- 星期名稱一律沿用現有的 `WEEK`（「週日」…「週六」）。

### 條件表單 `#planForm`

| 欄位 | id | 規則 |
|---|---|---|
| 目前等級／% | `#pl-from-lv`、`#pl-from-pct` | 等級為整數；% 為 0 ≤ % < 100。旁邊有「從練功記錄帶入」按鈕 `#pl-from-rec`，數值同經驗條（目前等級與本級已累積）；沒有啟用記錄時按鈕停用 |
| 目標等級／% | `#pl-to-lv`、`#pl-to-pct` | 同上；目標必須比目前高（同級時 % 要更高）。目標 % 預設 0（也就是「升到該等級」） |
| 起日 | `#pl-start` | 新增時預設**本地**今天，不是 UTC（見 tech-debt 第 12 項的坑） |
| 期限 | `#pl-span-n`、`#pl-span-unit` | 「X 天」或「X 個月」，換算成結束日 `end`（見行為規則）；旁邊即時顯示換算後的結束日 |
| 每週練功時段 | `#pl-weekly` | 1～4 組。每組：星期（可複選）＋開始＋結束（小時制，**15 分鐘的倍數**：`step="0.25"`，例如 19.25 表示 19:15）。`#pl-add-slot` 新增、每組有「刪」 |
| 每小時經驗 | `#pl-rate`、`#pl-rate-worker`、`#pl-rate-hist` | 數字輸入。旁邊顯示「歷史：X exp/h（N 筆、M 小時）」，`#pl-rate-worker` 選依哪位人員的記錄計算（預設全部），`#pl-rate-hist` 按下把歷史值填進輸入框 |
| 產生計畫 | `#pl-save` | 通過驗證才寫入；有計畫時按鈕名稱是「更新計畫」 |
| 刪除計畫 | `#pl-delete` | 有計畫時才顯示，先跳確認框 |

**預填規則**（編輯既有計畫時）：表單**一律用 `plan` 裡存的值預填**，不套用「預設今天」「帶入練功記錄」這類預設值：

- 起日＝`plan.start`（不重設成今天，否則過去的標記會全部掉出新計畫）。
- 期限顯示為「X 天」，`X = end − start + 1`（不還原成當初輸入的月數）。
- 目前等級／% 是 `plan.from`。要以現在的進度重新規劃，使用者自己按「從練功記錄帶入」；系統不會偷偷換掉起點。
- 每小時經驗是 `plan.rate`；歷史值只是旁邊的參考，按 `#pl-rate-hist` 才會填進去。

表單不會因為重畫而被清掉使用者正在輸入的內容（見「進行中的更新」）。

**預設與取整**（實作時的裁定，2026-10-06）：

- **新增模式**（沒有計畫）預設就帶入：起點＝「從練功記錄帶入」的值（有啟用記錄時）、起日＝本地今天、目標 % ＝ 0、預估時速＝歷史時速（有的話，`rateSrc` ＝ `history`）。編輯模式不套用任何預設，一律用 `plan` 存的值。
- **取整**：「用歷史值」與新增模式預填的預估時速取**四捨五入的整數**（快照存整數）；「從練功記錄帶入」的 % 取 **4 位小數**（顯示本來就是 4 位）。
- **目標 % 空白視為 0**；起點 % 空白不補，要使用者自己填（會報錯）。

### 摘要 `#planSummary`

1. 目標：`Lv51 30.5000% → Lv53 0.0000%`，期限 `2026-10-07 ～ 2026-12-31`（共 X 天、Y 個練功時段、Z 小時）。
2. 所需總經驗、**需要時速**（總經驗 ÷ 總時數）、**預估時速**（輸入的每小時經驗）。
3. **可行性**（沒填預估時速時顯示「未設定預估時速，無法判斷能不能達成」）：
   - 預估產出 ≥ 總經驗：綠字「依 X exp/h，預計 MM/DD 達成，比期限早 N 天」（早 0 天寫「剛好準時」）。
   - 預估產出 < 總經驗：紅字「依 X exp/h 只能完成目標的 N%。要準時達成需要 Y exp/h（要提高 P%），或把期限延到約 MM/DD」。
   - 延後日期用同一組每週時段往後找，找不到（3660 天內）顯示「—」。
4. **進度**：已完成 N／M 個時段、完成時數／總時數、**計畫經驗完成度**（完成時段的計畫經驗總和 ÷ 總經驗），一條進度條，同時用刻度標出「應有進度」（已結束時段的計畫經驗總和 ÷ 總經驗）。
5. **有沒有落後**：
   - 已結束但還沒填的時段數（待填）。
   - 落後：已結束但標記不是「完成」的時段（待填＋沒練）有 1 個以上時，寫「落後 X 個時段（約 Y exp、Z%）」，Y ＝「已結束且非完成」的時段的計畫經驗加總（不用「應有進度 − 完成度」，未結束時段上有完成標記時差值會變小甚至為負）；否則「進度符合計畫」。
   - **補救時速**：照目前完成度，剩下還沒結束的時段要 `(總經驗 − 完成的計畫經驗) ÷ 剩餘時數` exp/h 才補得回來，並跟預估時速並排。
6. 「這些數字是依你輸入的時速估算的計畫值，不是實際獲得的經驗」，摘要底下固定一行小字。
7. 歷史時速與「人員效率」表上的每小時經驗**算法不同**：計畫的歷史時速只計入等級表有經驗的記錄（見 [calculations.md](../calculations.md#歷史時速-planhistrateworkerid)），所以兩個數字可能不一樣，歷史欄位旁加一行小字說明。

## 行為規則

### 計算

見 [calculations.md](../calculations.md#練功計畫)。重點：

- 所需經驗用等級表的「升下一等經驗」逐級加總，扣掉起點已經有的、加上終點要的。
- 每個時段的目標 = **需要時速 × 該時段時數**，所以整張表剛好在最後一個時段結束時到達目標；不是依預估時速分配。
- 等級表缺少任何一個必要等級的升級經驗（沒有那一列、經驗是 0 或不是數字）時**不產生計畫**，紅字指名缺哪一級，請使用者先去補等級表。必要等級：從起點等級到「目標等級 − 1」，以及目標等級本身（只有目標 % > 0 時才需要）。
- 用到可信度是「推估」的等級時，摘要加一行「含推估的等級經驗，實際可能有出入」。

### 期限換算

- 「X 天」：結束日 = 起日 + (X − 1) 天，起日當天算第一天。X 為 1～366 的整數。
- 「X 個月」：結束日 = 起日加 X 個月（日數超過該月月底時取月底）再減 1 天。X 為 1～12 的整數。
- 起日必須是存在的日期（`normDate`）；整段期間最長 366 天。
- **展開後的時段總數最多 1000 個**，超過不產生計畫：「時段太多（N 個，上限 1000），請縮短期限或減少時段」。這是為了讓 `marks` 的大小有確定的上限，見 [format.md](../format.md#plan練功計畫)。

### 時段（每週模板）

- 一組模板 = 星期的集合＋開始＋結束，每週重複。展開成實際時段時，起日到結束日（含）的每一天，凡星期有被勾的，每一組都產生一個時段。
- **不支援跨午夜**（董事長 2026-10-06 裁示，首版已知限制，記在 tech-debt）：要求 `0 ≤ 開始 < 結束 ≤ 24`。要練過午夜請拆成兩組（例如 22–24 與隔天 0–2）。理由：跨午夜會讓「進行中」「屬於哪一天」「標記鍵」「重疊判斷」都複雜很多。
- 開始與結束都要是 **15 分鐘的倍數**（`x × 4` 是整數）。這同時讓標記鍵的長度有上限、分鐘數一定是整數。
- 同一個星期內，兩組模板的時間不能重疊（`開始₁ < 結束₂ 且 開始₂ < 結束₁` 就算重疊），紅字指出是哪兩組。
- 整段期間展開後沒有任何時段時，不產生計畫：「這段期間沒有任何可練的時段」。

### 時段狀態（用本機時間）

時段的開始、結束時刻用**時段所屬日期的本地時間**建立：把日期字串拆成年、月、日，呼叫 `new Date(年, 月-1, 日, 時, 分)`（小時數換成整數的時與分，因為是 15 分鐘的倍數所以不會有小數分鐘）。**不要用 `new Date("YYYY-MM-DD")`**：那是 UTC 午夜，在台灣會差 8 小時。另一方面，「這天是星期幾」仍然沿用 `weekday()` 的 UTC 算法（從日期字串算，與時區無關），兩者不衝突。

依現在時刻分成：

| 狀態 | 條件 | 畫面 |
|---|---|---|
| 未開始 | 現在 < 開始 | 第一個未開始的時段加「下一個」標籤 |
| 進行中 | 開始 ≤ 現在 < 結束 | 整列 highlight，加「進行中」標籤 |
| 已結束 | 現在 ≥ 結束 | 沒有標記時顯示「待填」，並出現 `完成`、`沒練` 兩個按鈕 |

- **highlight 不能只靠顏色**：除了底色與左邊框，還要有「進行中」文字標籤，並在該列加 `aria-current="true"`。
- 已標記的列：`完成` 顯示「✔ 完成」，`沒練` 顯示「✘ 沒練」，旁邊一個小按鈕「改」。再按同一個狀態的按鈕或「改」可以清除標記，回到「待填」。
- `完成`／`沒練` 按鈕只在**時段結束後**出現（需求如此）。時段還沒結束的列沒有按鈕。
- **標記一律照存的值顯示與計算**，不管時段現在是什麼狀態：系統時間往回調、或匯入的資料在還沒結束的時段上有標記時，這個標記照樣顯示、照樣計入完成度；「改」按鈕只要有標記就會出現，才清得掉。
- 沒有任何自動標記：「待填」就是待填，不會因為過了時間就變成「沒練」。

### 標記的寫入

- 按下按鈕改 `db.plan.marks` 後走一般流程：`persist()`＋重畫計畫頁。因此會更新 `db.meta.updatedAt`、寫進 localStorage，並由 `cloudMarkDirty()` 把這台標成「有未上傳的修改」（連結雲端時 2 秒後自動上傳；雙邊都改過時照常進衝突對話框，不會悄悄覆蓋）。
- 讀不出原本資料（`loadProblem`）的期間 `persist()` 回傳 false，標記只存在畫面上、不寫入也不上傳，狀態列照現有的說法提示「自動儲存已暫停」；計畫頁不另外處理。
- 標記不會建立或修改任何 `sessions`。

### 進行中的更新

- 計畫頁顯示時，每 30 秒（以及頁面從背景回到前景時）檢查一次「狀態簽章」：所有時段的狀態（未開始／進行中／已結束）加上「下一個」是哪一個，**只有簽章改變時才重畫**摘要與表格，所以大部分的檢查什麼都不做，不會干擾捲動與鍵盤焦點。
- 重畫前記下目前取得焦點的按鈕（用 `data-key` 與動作識別），重畫後把焦點還給同一顆按鈕（還在的話）；捲動位置不變。
- 計時器只在 `tab === "plan"` 而且 `document.hidden === false` 時檢查；切到別的頁籤就不做事。
- 計時器**絕不呼叫 `persist()`**，只有使用者按按鈕才會寫資料。
- 表單不在重畫範圍內，使用者正在輸入時不會被打斷。

### 計畫資料的檢查 `planCheck(plan)`

回傳錯誤清單（空陣列＝可用）。畫面、計算都只用通過檢查的計畫；沒通過時顯示「計畫資料無法使用」與原因。規則：

1. `plan` 是物件；`v` 是 1（`v` 大於 1 視為「是比較新版本存的計畫，這個版本看不懂」，不當成損壞，訊息要這樣寫，**同樣不刪**）。
2. `start`、`end` 是 `normDate` 認得的日期，`end ≥ start`，整段 ≤ 366 天。
3. `from`、`to` 是物件，`level` 是整數、`pct` 是 0 ≤ % < 100 的有限數；目標高於起點（同級時 % 更高）。
4. `weekly` 是陣列，長度 1～4；每組的 `days` 是非空陣列、值為 0～6 的整數且不重複；`start`、`end` 是有限數、`0 ≤ start < end ≤ 24`、都是 0.25 的倍數；同一星期內不重疊。
5. `rate` 是 `null`、**缺少（視為 `null`，不算錯）**、或有限數且 ≥ 0；`rateSrc` 是 `"history"` 或 `"manual"`（缺少視為 `"manual"`）；`rateWorker` 是字串（缺少視為空字串）。
6. `marks` 是物件，**缺少視為 `{}`（不算錯；載入與匯入都不補，讀取時用 `plan.marks || {}`）**；鍵數 ≤ 1000；每個鍵符合 `YYYY-MM-DD|開始|結束`（日期存在、開始結束是 0.25 的倍數且 0～24）；整個 `plan` 的 `JSON.stringify` 長度 ≤ 40000 字元（單格上限的保險）；值是 `"done"` 或 `"missed"`（其他值：忽略這個標記，不算錯）。
7. 展開後時段總數 ≤ 1000、總時數 > 0。
8. 等級表的必要等級都有經驗（這一條是**計算時**檢查，補上等級表就恢復；訊息要指名缺哪一級）。

### 更新與刪除計畫

- 「更新計畫」會依新條件重新展開所有時段。**已標記的時段，標記只在「同一天同一個開始與結束時間」仍然存在時保留**；不在新計畫裡的標記會被清掉。
  - 會有標記被清掉時，先跳確認框：「已標記的 N 個時段不在新計畫裡，更新後這些標記會被清掉。」
  - 沒有標記會被清掉時，不問。
- 「刪除計畫」：確認框寫明「已標記的 N 個時段也會一起刪掉」。

### 整份資料被換掉時（匯入、開檔、還原示範、清空、雲端）

`plan` 是 `db` 的一部分，整份資料被換掉時計畫會跟著換。**目前有計畫（`db.plan` 是物件）時，下面每一條路徑都要先確認，確認框要講明計畫與已標記的時段數**；沒有計畫的人完全不受影響（維持現行行為）。

| 路徑 | 現況（程式） | 新行為 |
|---|---|---|
| 匯入 JSON（`#fileInput`） | `confirmReplaceUnreadable()`：平常不問，讀不出資料或已連結雲端才問 | 有計畫時也問：`confirmReplaceUnreadable()` 再加一個條件，並在訊息附 `planReplaceWarning()`：「目前的練功計畫（N 個已標記的時段）會被換掉；檔案裡沒有計畫的話，計畫會消失。」 |
| Electron 開啟檔案（`#btnOpenFile`） | 同上，共用 `confirmReplaceUnreadable()` | 同上（同一個函式，一起改） |
| 還原示範資料（`#btnDemo`） | 本來就有確認框 | 訊息附 `planReplaceWarning()` |
| 清空全部（`#btnReset`） | 本來就有確認框 | 訊息附 `planReplaceWarning()` |
| 雲端「用雲端的」取代這台（`cloudTakeCloud`） | 只有雲端改過、這台沒改過時不問（這台內容＝雲端上一版）；有改過時走衝突對話框 | **維持不問**：因為標記會讓這台變成「有修改」（見「標記的寫入」），所以不會有未上傳的計畫被悄悄蓋掉。衝突／第一次連結的對話框（`cloudAsk`）在「這台」「雲端」兩行底下各加一行練功計畫概況：「練功計畫：有（N 個已標記的時段）」或「練功計畫：沒有」，讓使用者選的時候看得到。雲端那行的 `plan` 取自尚未 normalize 的 `fromSheets` 結果，**取之前要先用 `isPlainObj` 判斷 `plan`、`marks` 是物件**才數標記，否則壞掉的雲端資料會讓對話框拋例外 |

`planReplaceWarning()` 在沒有計畫時回傳空字串。已連結雲端時，它與現有的 `cloudReplaceWarning()` 並列，不互相取代。

### 匯出入與同步

- 匯出 JSON 自然包含 `plan`；CSV 不含（CSV 本來就只放記錄）。
- Google 試算表同步：`plan` 是 `db` 的頂層「未知欄位」，`toSheets()` 會把它放進「設定」工作表的「其他欄位（JSON）」那一列，`fromSheets()` 讀回來，**不需要改試算表的欄位或工作表結構**，舊試算表（沒有 `plan`）照常讀，`sheetProblem()` 不會把有 `plan` 的試算表判成壞掉（它只檢查欄位名與「設定」的鍵）。細節與大小上限見 [format.md](../format.md#plan練功計畫) 與 [cloud-sync.md](cloud-sync.md)。

## 資料

見 [format.md](../format.md#plan練功計畫)。簡述：`db.plan` 是選填的頂層物件，沒有就是沒有計畫。只存「條件」與「標記」：

```json
"plan": {
  "v": 1,
  "start": "2026-10-07", "end": "2026-12-31",
  "from": {"level": 51, "pct": 30.5}, "to": {"level": 53, "pct": 0},
  "weekly": [{"days": [1,2,3,4,5], "start": 19, "end": 23}],
  "rate": 300000, "rateSrc": "history", "rateWorker": "",
  "marks": {"2026-10-07|19|23": "done"},
  "created": "2026-10-06T00:00:00.000Z"
}
```

展開後的時段、目標位置都是**即時算出來的，不存**（跟全站「只存原始觀察值」的原則一致）。

## 邊界情況

- **沒有計畫的舊資料**：`db.plan` 不存在，計畫頁只顯示說明與表單，其他頁完全不受影響。
- **計畫資料壞掉**（手改、匯入的怪資料，`planCheck()` 回傳錯誤）：計畫頁只顯示「計畫資料無法使用：原因」與「刪除這份計畫」按鈕；**不拋例外、不影響其他頁籤、不自動刪除**。這份壞資料還在 `db` 裡時，Google 同步可能因為單格太大而失敗，原因行要提醒這一點（只有 `marks` 超過 1000 個這類可能超過上限的錯誤才加）。
- **計畫頁自己的 try／catch**：這一頁出錯時只顯示「練功計畫頁顯示失敗，資料本身沒有受影響」。
- **等級表之後被改**（補上、改了升級經驗、刪了某級）：因為時段目標是即時算的，計畫會跟著用新的經驗重算；若變成缺級，進入「無法使用」狀態，等級補回來就恢復。**標記不會因此消失。**
- **預估時速是 0 或空白**：照常產生計畫，只是沒有可行性判斷與預估達成日。
- **歷史時速算不出來**（沒有啟用且有經驗的記錄，或選的人員沒有記錄）：顯示「歷史：無資料」，`#pl-rate-hist` 停用，使用者要自己填。
- **`rateWorker` 指到已刪除的人員**：維持 `rate` 當時的快照值，歷史欄位提示「找不到這位人員」，不悄悄換成別人。
- **今天不在計畫期間內**：沒有特殊處理；計畫還沒開始時第一個時段是「下一個」，計畫已結束時所有列都是已結束。
- **使用者把系統時間調來調去**：狀態都是依現在時刻即時算的，標記不會因此改變。

## 設計決策

- **存在 `db.plan`，不是獨立的 localStorage key**：使用者選的方案。好處是跟匯出 JSON、Google 同步一起走、換裝置不會丟；代價是動到資料格式（已獲核准），以及計畫會被「整份資料取代」的動作一起換掉（所以有計畫時要先確認，見上表）。
- **新頁籤，不改原本兩頁**：同每日進度頁的設計決策（使用者要求不動到原本的版面）。
- **每個時段的目標用「需要時速」分配**：計畫的意義是「照這個節奏就能準時到」；預估時速只拿來判斷可不可行，不拿來改計畫。否則使用者看到的表會永遠「剛好達成」，失去提醒的作用。
- **預估時速預設取歷史、可覆寫、可選人員**：天堂看不到單怪經驗，唯一有根據的是自己記錄的時速；但代練與自己練的時速不同，所以可以選人員。快照存進 `rate`，不隨新記錄自動變：計畫的目標與進度不能自己漂移。要更新時使用者按 `#pl-rate-hist` 再「更新計畫」。
- **標記只能在時段結束後填**：需求如此。代價是提早練完的使用者要等到結束時間才能標記（首版限制，見 tech-debt）。
- **不自動寫入練功記錄**：「完成」只是勾選，不會替使用者新增 `sessions`。實際獲得多少%仍由使用者在練功記錄頁登錄，避免計畫值污染真實資料。
- **不支援跨午夜、一次只有一份計畫、沒有通知提醒**：首版範圍；跨午夜是董事長 2026-10-06 裁示的已知限制。
- **期限最長 366 天、模板最多 4 組、展開後時段最多 1000 個、時間是 15 分鐘的倍數**：讓 `marks` 有確定的大小上限（見 [format.md](../format.md#plan練功計畫) 的容量估算），因為整份 `db` 的頂層未知欄位要塞進試算表的**一個儲存格**（Google 單格上限 50,000 字元）。只限制天數與模板數不夠：4 組 × 366 天最多會有 1464 個時段；不限制小時的精度，`19.333333333333332` 這種值會讓一個鍵長到約 60 字元。
- **雲端取代不額外確認**：標記走 `persist()`，會讓這台變成「有修改」，真的有未上傳的計畫時一定會進衝突對話框，不用另外問；多問會和「只有雲端改過就直接下載」的既有規則打架。

## 修改時要檢查

- **數字**：已知答案的小例子手算比對（單級、跨一級、跨多級、目標 % > 0、起點 % > 0、同級 a = b）；最後一個時段的目標位置要等於目標位置（顯示的 4 位小數相同）；所有時段的計畫經驗加總等於所需總經驗；**超大的升級經驗**（例如 1e10）時進位仍正確、不會顯示 `-0.0000%` 或 `100.0000%`（見 calculations.md 的容許誤差）。
- **等級表缺級**：缺中間級、缺目標級（目標 % = 0 時不需要）、升級經驗 0、推估等級的提示。
- **時段**：多組模板、跨週、同一天兩組、重疊被擋、`end ≤ start` 被擋、非 15 分鐘倍數被擋、`end = 24`、1 天與 366 天、X 個月的月底、超過 1000 個時段被擋。
- **時間**：用假的 `Date` 測進行中／下一個／已結束／計畫前／計畫後；邊界剛好等於開始、剛好等於結束；系統時區設成 UTC 與 UTC+8 結果相同（沒有用到 `new Date("YYYY-MM-DD")`）。
- **標記**：結束後才有按鈕；清除；未結束時段上的標記（匯入的資料）照樣顯示與計算且清得掉；更新計畫時保留與清掉的情形與確認框；刪除計畫；標記後 `cloud.dirty` 變 true、`db.meta.updatedAt` 更新；`loadProblem` 期間標記不寫入。
- **重畫**：狀態簽章沒變時不重畫；重畫後鍵盤焦點與捲動位置還在；計時器在別的頁籤不做事、不寫資料。
- **資料**：載入含舊資料（沒有 `plan`）時 `db` 逐位相同；`plan` 壞掉（字串、陣列、`marks` 是陣列、`weekly` 缺、`v` 是 2）不影響其他頁，且載入時**不被刪、不被改**（只有數字文字轉成數字）；匯入時 `plan` 不是物件被拿掉並回報；匯出再匯入、`toSheets` → `fromSheets` 來回後 `plan` 完全相同；容量最壞情況（1000 個時段全標記、開始結束是 15 分鐘倍數）序列化後小於 50,000 字元。
- **換資料確認**：有計畫時匯入、開檔、還原示範、清空都會問而且訊息講明標記數；沒計畫時行為與 main 逐項相同（尤其匯入平常不問）；`cloudAsk` 多了計畫概況那一行。
- **同步**：用模擬 Google 跑雙邊都改過的情境，確認標記一個時段會讓這台被視為「有修改」；有 `plan` 的資料上傳再下載回來完全相同；舊試算表（沒有 `plan`）照常讀。
- **畫面**：320～1600px 兩個舊頁籤不溢出、901px 以上舊兩頁與 main 逐元素相同（只多一個頁籤）；`#pageTabs` 鍵盤操作三個頁籤；`aria-current`；375px 卡片版。
- **安全**：所有放進 `innerHTML` 的文字（人員名稱、錯誤訊息裡的鍵或日期）一律 `esc()`；`billHours` 為 0 的記錄不影響歷史時速。
- **文件**：依 [development.md](../development.md#文件維護) 一併更新 `layout.md`（頁籤、寬度分界）、`architecture.md`（新區段、`planPage` 等全域狀態、UI key）、`cloud-sync.md`（`plan` 隨「其他欄位」同步、`cloudAsk` 的計畫概況行）、`file-io.md`（匯入／清空的新確認框）、根目錄 `README.md`、`tech-debt.md`（跨午夜、結束後才能標記、一份計畫）；`privacy.html` 不需要改（沒有新的資料流向、存放位置與 Google 權限都沒變），但要在審查時確認。
