# Grind Log 通用格式 v1

一種記錄「分母會變動的進度」的通用資料格式。

## 為什麼需要這個格式

用「每小時獲得幾 %」比較效率是錯的。每一級的 % 代表的實際量不同 —— 51 等的 1% 是
553,488 點經驗，53 等的 1% 是 671,282 點。同樣的打怪速度，等級越高 %/hr 看起來越差。

這個格式的原則是：**只儲存原始觀察值，所有效率指標都用算的。**

只要換掉 `levels` 對照表，同一套工具可以記錄任何有階段門檻的進度 —— 遊戲練等、
證照時數、健身課表、外包計件。

## 結構

```json
{
  "schema": "grind-log/v1",
  "meta": {
    "title": "天堂經典版 練功記錄",
    "unit": "exp",
    "currency": "TWD",
    "updatedAt": "2026-09-06T00:00:00.000Z"
  },
  "levels": [
    { "level": 51, "required": 55348837, "confidence": "measured", "note": "" },
    { "level": 53, "required": 67128205, "confidence": "estimated", "note": "x1.10 外推" }
  ],
  "workers": [
    { "id": "me",   "name": "我",   "hourlyRate": 0,     "billable": false, "note": "自己練，不計費" },
    { "id": "hire", "name": "代練", "hourlyRate": 200,   "billable": true,  "note": "日薪1600÷8h" }
  ],
  "sessions": [
    {
      "id": "s1",
      "date": "2026-09-01",
      "start": 7,
      "end": 10,
      "workerId": "me",
      "level": 51,
      "gainedPct": 4,
      "enabled": true,
      "note": ""
    }
  ]
}
```

## 欄位

### meta
| 欄位 | 型別 | 說明 |
|---|---|---|
| `title` | string | 這份記錄的名稱 |
| `unit` | string | 進度單位名稱，如 `exp`、`小時`、`件` |
| `currency` | string | 費用幣別 |
| `updatedAt` | ISO 8601 | 最後修改時間 |

### levels
階段門檻對照表。`level` 是階段編號，`required` 是**該階段升到下一階段**所需的總量。

`confidence` 用 `measured`（實測）或 `estimated`（推估）標記資料可信度，介面會把
推估值標成不同顏色，避免拿估值當事實用。

### workers
| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | string | 唯一識別碼，`sessions.workerId` 參照它。可省略，讀入時自動編號 |
| `name` | string | 顯示名稱 |
| `hourlyRate` | number | 時薪。日薪請自行換算，或設 0 表示不計費 |
| `billable` | boolean | 是否計入費用統計 |

### sessions
| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | string | 記錄識別碼，改、刪用它找記錄。**可省略**，讀入時自動編號 |
| `date` | `YYYY-MM-DD` | 開始日期 |
| `start` / `end` | number | 小時制，可用小數（`3.5` = 3:30）。`end` 小於 `start` 視為跨午夜 |
| `workerId` | string | 參照 `workers.id` |
| `level` | number | 該時段所處階段 |
| `gainedPct` | number | 該時段獲得的百分比 |
| `billableHours` | number | null | 實際計費／有效時數。**省略或 `null` 視為等同時段長度** |
| `enabled` | boolean | 是否列入統計。**省略視為 `true`**，所以舊檔可以直接匯入 |

**跨階段的時段**請拆成兩筆分別記錄，否則換算會有誤差。

### 為什麼時段長度不等於計費時數

真人代練的時段含休息。休息時間**既不計費，也不會產生進度**，所以
`billableHours` 同時是費用和效率的分母，`start`/`end` 只描述佔用的時間窗。

例：時段 10:00–18:00（8 小時）但實際計費 7 小時 —— 費用算 7 小時，
每小時經驗也除以 7。若改用 8 去除，算出來的效率會比代練自己的記錄低 12.5%。

留空的話兩者相同，所以不需要計費概念的資料（自己練、機器掛網）不必填。

`enabled: false` 的時段仍會留在檔案裡、也照樣顯示在記錄表，只是不計入任何統計
（經驗條、人員效率、時數、費用都跳過）。用來排除維修中斷、測試資料，或試算
「少請一個打手會差多少」，不必真的把記錄刪掉。

## 推導公式

所有指標都不儲存，由原始值即時計算：

```
hours          = end >= start ? end - start : end + 24 - start   ← 時段長度（跨午夜 +24）
billHours      = billableHours ?? hours       ← 計費／有效時數
requiredUnits  = levels 裡第一列 level 相同的 required
gainedUnits    = gainedPct / 100 × requiredUnits
unitsPerHour   = gainedUnits / billHours      ← 唯一可跨階段比較的效率指標
pctPerHour     = gainedPct / billHours        ← 僅限同階段內比較
cost           = billable ? billHours × hourlyRate : 0
costPerMUnit   = cost / (gainedUnits / 1e6)   ← 可跨階段比較的成本指標
```

效率和費用的分母都是 `billHours`，理由見上一節。
實作細節，例如怪資料怎麼處理、分母是 0 時怎麼顯示，見 [calculations.md](calculations.md)。

## 讀入時的整理

檔案可能是手改的、舊版的，或格式不對。讀進來時會先整理成上面的型別，
**格式正確的資料經過整理不會有任何改變**。

整理分成兩種情境，規則不同：

- **匯入**（匯入 JSON、開啟檔案）：使用者主動、會看到訊息，所以可以略過沒用或重複的列
- **載入**（開啟網頁時從 localStorage 讀）：那是使用者現有的資料，他看不到任何訊息，
  所以**只做不會掉資料的轉換，一列都不刪**

| 情況 | 處理 | 載入時也做 |
|---|---|---|
| 數字寫成十進位文字（`"10"`、`"1.5"`） | 轉成數字。`"0x33"` 這類非十進位不猜 | ✔ |
| 日期沒補零（`2026-9-5`） | 補成 `2026-09-05` | ✔ |
| 日期不存在或認不得（`2026-09-31`） | 保留原樣，每日進度頁列在「日期不明」 | ✔ |
| 數值認不得（`"5%"`） | 保留原樣，計算時不採用 | ✔ |
| 空字串的數值欄位 | 當成空值 | ✔ |
| 計費時數認不得或是負數 | 當成空值（等同時段長度） | ✔ |
| 數值欄位塞了物件、陣列、布林 | 拿掉 | ✔ |
| 文字欄位塞了物件、陣列 | 清空（布林會變成 `"true"`／`"false"`） | ✔ |
| `sessions` 等陣列裡混了非物件 | 略過 | ✔ |
| 記錄沒有 `id` | 自動編號 | ✔ |
| 記錄的 `id` 重複 | 重新編號（記錄的 id 沒有被其他地方參照） | ✔ |
| `id`、`workerId` 裡的換行等控制字元 | 移除 | ✔ |
| 人員沒有 `id`（或整理後是空字串） | 自動編號成 `w-noid-1`、`w-noid-2`…（避開人員與記錄已經在用的 id），原本對到他的記錄（`workerId` 沒填或空白）跟著換；有多位沒有 id 時，匯入訊息會提醒確認記錄有沒有對到對的人 | ✔ |
| 人員 `id` 整理後撞在一起（`"a"` 和 `"a "`、`1` 和 `"1"`） | 後面那位換成新 id，記錄的 `workerId` 跟著換 | ✔ |
| 等級表沒有有效的 `level` | 略過 | ✘ 保留 |
| 等級表的 `level` 重複 | 保留第一列，其餘略過 | ✘ 保留 |

匯入後的訊息會列出整理了哪些東西；只有補零、自動編號這類無害的整理時顯示綠字，
有資料被拿掉或認不得時顯示紅字。

**匯入是整份取代，而且是原子的**：新資料先在畫面上試畫一次，成功才寫進
localStorage；中途出錯就退回原本的資料，顯示「讀不了這個檔案」。

**載入時讀不懂**（例如 localStorage 裡的內容不是有效的 JSON）：不會改用示範資料。
原文另外備份到 `grind-log/v1:unreadable`（那一格已經有另一份不同的內容時，另存成
`grind-log/v1:unreadable-<時間戳>`；同一份原文已經備份過就不再寫，重新整理不會越存越多份），
畫面顯示空白，**自動儲存暫停**，直到使用者自己匯入、還原示範資料或清空全部。
這段期間的修改不會存下來，但原本的資料也不會被覆蓋。

這段期間頁首會一直顯示紅框提示（不會被其他訊息蓋掉），附「下載原始內容」按鈕：
下載的是讀不出來的原文，用文字編輯器修好後再用「匯入 JSON」載入即可救回。
注意「匯出 JSON」匯出的是目前畫面上的資料（包含暫停期間新增、但沒存下來的內容），不是原文。
儲存空間不足、連備份都寫不進去時，提示會說明原文雖然還留著，但匯入、還原示範資料或
清空全部會把它蓋掉，要先下載。這三個動作在這段期間都會先跳確認框提醒下載
（平常的匯入不會問）。

換上的新資料如果寫不進 localStorage（儲存空間不足，或瀏覽器不允許這個網站存資料），
訊息會用紅字說明。這時若原文**沒有**另外備份，提示和「下載原始內容」會留著、繼續暫停自動儲存
——原文還在 localStorage 裡，是唯一的一份，不能讓之後的存檔把它蓋掉；畫面上的新資料請用
「匯出 JSON」另存。原文已經備份過時則照常恢復自動儲存。

## 相容性

- 匯出的 JSON 可直接餵給任何實作，不依賴任何執行環境。
- CSV 匯出為扁平化的 sessions（含推導欄位），供試算表使用；CSV 不是主格式，
  因為它無法承載 `levels` 與 `workers`。
  以 `=`、`+`、`-`、`@`（含全形 `＝＋－＠`，或 Tab、換行）開頭的文字前面會加一個 `'`，
  避免試算表把人員名稱、備註這類內容當成公式執行；數字（包括負數）照原樣輸出。
- 未知欄位一律保留不刪，方便日後擴充。
